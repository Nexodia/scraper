# ADR-001: Estrategia de extracción de precios

Status: Accepted

Date: 2026-11-01

## Context and Problem Statement

Debemos extraer el precio (y metadatos) de productos desde 5 sitios chilenos de e-commerce con
patrones técnicos distintos:

| Sitio | Plataforma | Patrón |
| --- | --- | --- |
| dartel.cl | VTEX | datos estructurados (JSON-LD) + API de catálogo |
| vitelenergia.com | Magento 2 (Hyva) | server-rendered + meta tags + GraphQL |
| rhona.cl | MIPLUS CMS (legacy) | solo HTML visible (sin datos estructurados) |
| tiendatecnored.cl | Magento | server-rendered + meta tags |
| shop.sonepar.cl | SPA propia (Checkbuy) | shell + API JSON interna (requiere auth) |

No existía evidencia de qué método de extracción alcanza los umbrales de exactitud con el menor
costo, ni de si una capa de verificación agéntica se justifica.

## Decision Drivers

- Exactitud de precio ≥ 95 % sobre páginas cubiertas (R4).
- Cobertura ≥ 80 % (R5).
- p95 de latencia ≤ 15 s (R6); costo por página acotado (R7).
- Respetar robots.txt/ToS, sin bypass de CAPTCHA (R8); secretos solo en `.env` (R9).
- Trazabilidad y reproducibilidad de cada extracción (R10).

## Considered Options

- A1: crawler clásico (selectores CSS).
- A2: datos estructurados (JSON-LD / meta tags).
- A3: headless browser (Playwright) + selectores.
- A4: extracción LLM (Gemini flash-lite, salida JSON).
- A5: A4 + verifier agéntico (segunda pasada LLM).
- A6: **híbrido determinista-first con routing por sitio + API autenticada para la SPA** (LLM como
  fallback opcional).

## Decision Outcome

Se adopta **A6**: arquitectura híbrida con routing por patrón de sitio.

- VTEX (dartel) → JSON-LD / API de catálogo.
- Magento (vitelenergia, tecnored) → meta `product:price:amount` (+ GraphQL opcional).
- Legacy sin datos estructurados (rhona) → selector CSS visible.
- SPA restringida (sonepar) → API autenticada `products/client/details` (OAuth2 guest).
- LLM (A4) como **fallback** para sitios futuros donde el determinista falle; **no** en el camino
  por defecto. Browser (A3) y verifier (A5) **no** se usan en el camino por defecto.

## Rationale

La evidencia del spike SP1 muestra que:

1. Cada sitio tiene un método determinista que alcanza 100 % (salvo la ambigüedad multi-variante de
   vitelenergia #4, que **ningún** método resuelve releyendo el mismo HTML).
2. El browser (A3) **no añade exactitud** frente al determinista: misma exactitud a ~9,4 s vs 2,6 ms.
3. El LLM (A4) **empata pero no supera** al determinista (19/20 = 95 %) a ~11,5 s/ítem, ~1,2 M
   tokens y con límites de cuota (429).
4. El verifier (A5) **añadió 0 exactitud**: confirmó el único error real en lugar de corregirlo.
5. La API es imprescindible solo para sonepar (la API anónima devuelve `price: {}`).

El MCDA da a A6 **94,55** frente a 76,60 (A4) y 74,10 (A3); la decisión es **estable** ante
variaciones de ±0,10 en cualquier peso.

## Evidence

- SP1: spike de extracción de precios (P0–P5).
- E1: A1 CSS → `data/evidence_p2.json` (48 %).
- E2: A2 estructurado → `data/evidence_p2.json` (56 % solo; 100 % en dartel/tecnored).
- E3: A3 browser → `data/evidence_p3.json` (76 %, ~9,4 s).
- E4: APIs → `data/evidence_p3_apis.json` (sonepar 100 %, VTEX 100 %, GraphQL 60 %).
- E5: A4 LLM → `data/evidence_p4.json` (76 %; 95 % sobre no-sonepar).
- E6: A5 verifier → `data/evidence_p4.json` (error_reduction = 0).
- E7: matriz consolidada + MCDA → `data/evidence_summary.json`, `data/evidence_mcda.json`.
- Gold set y capturas: `data/gold_set.draft.json`, `data/raw/`.

## Positive Consequences

- 96 % de exactitud (24/25) y 100 % de cobertura, al costo y latencia de un determinista.
- Sin cuota LLM ni latencia de browser en el camino por defecto.
- Guardrails deterministas reutilizados del scaffold (mínimo privilegio, allow-list de dominios).
- Sonepar resuelto cumpliendo ToS (login manual una vez; refresh grant estándar; sin bypass de
  CAPTCHA).

## Negative Consequences

- Una ruta por sitio = configuración por patrón (más piezas que un único extractor genérico).
- Sonepar requiere una sesión autenticada que expira (refresh token rotativo) y precios por cliente.
- El fallback LLM introduce una dependencia de proveedor y costo si llegara a activarse con frecuencia.

## Risks and Limitations

- Gold set pequeño (25 productos, 5/sitio); exactitud indicativa, no estadísticamente concluyente.
- Fingerprints a nivel de homepage; productos individuales pueden variar.
- La ambigüedad multi-variante (vitelenergia #4) es un problema de datos, no de método.
- La robustez ante cambios de markup (drift) no fue simulada; solo se estimó cualitativamente.
- Precios de sonepar dependen del cliente/ubicación del guest login.

## Revisit Conditions

Revisar este ADR si:

1. Aparece un sitio cuyo precio solo renderiza por JS **y** sin datos estructurados **y** sin API
   → reevaluar A3 (browser) o A4 (LLM).
2. La deriva de markup rompe > 5 % de los selectores deterministas → activar fallback LLM y medir.
3. El costo del LLM baja sustancialmente (p. ej. un modelo más barato como DeepSeek/Flash-Lite) →
   reevaluar LLM como camino por defecto.
4. Sonepar cambia su API/auth o deja de ofrecer guest login.
5. El gold set crece y la exactitud medida cae bajo los umbrales.
